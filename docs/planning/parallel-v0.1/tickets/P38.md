# P38 在 Web 审核并应用 Proposal

## Parent

[并行交付计划](../spec.md)；原任务 [#34](https://github.com/CaiZongyuan/knowmesh/issues/34)、[#39](https://github.com/CaiZongyuan/knowmesh/issues/39)。

## What to build

用户从 Proposal 队列打开结构化 diff，核对 Schema 与原始 Evidence，逐项编辑、接受或拒绝，最后按策略预览并确认 Apply。交付这一审核闭环所需 HTTP、生成客户端和 Web 页面，所有变更继续调用已实现的 Proposal Core。

## Acceptance criteria

- [ ] Proposal 队列支持有界分页与状态筛选，详情可读取当前和历史 revision；HTTP 覆盖已有 create/get/edit/revalidate 及审核动作，Schema patch 读取服务结构化审核，不新增同义契约。
- [ ] 页面按 create/update/merge/conflict/warning 展示结构化项目、before/after、目标文件和汇总；Evidence 可定位到 P34/P35 的固定 revision 上下文，用户无须审核原始 JSON。
- [ ] Accept/Reject/Edit 与重新验证传递 expected revision 和幂等键；编辑后旧审核不能继续有效，并发修改或过期输入显示真实冲突，不覆盖他人结果。
- [ ] strict 模式存在 pending 或 blocked 项时不能 Apply；relaxed 模式的已接受子集及批量接受行为完全遵守 Core 策略，不能用前端状态替代服务端检查。
- [ ] Apply 前执行真实 dry-run 并展示变化及风险，用户明确确认后才写入；stale/hash/policy 不匹配在 HTTP 与 UI 两侧均可观察且不产生规范修改。
- [ ] 成功后展示原始 changed paths、generation 和 reconcile report，并失效受影响 Query；丢失响应重试返回原结果，不重复应用。
- [ ] 浏览器测试覆盖 relaxed/strict、逐项编辑、拒绝、stale、并发 revision、键盘审核和 Apply 后重新搜索；OpenAPI 与生成客户端无漂移。

## Scope and handoff

本票拥有既有 Proposal 的审核到 Apply 表面，以及 proposal.create 和 schema.patch 的 HTTP 契约与测试；不重做 Builder、review hash、事务或持久幂等。前置输入是 P02/P03 的队列及批量行为、已实现的 Proposal 生命周期和 P34/P35 证据导航。用 CLI、create HTTP 或固定 fixture 创建待审核 Proposal 即可独立验收，无须等待 Compiler 或 Ask。

共享热点是 Proposal HTTP 路由、OpenAPI、生成客户端、Inspector、Query 失效规则与路由树。本票包含多种审核状态，执行前必须确认其全部 Core 操作已经落地；若新增领域行为超过单上下文，应先反馈拆分提案，而非在 UI 票内扩展 Proposal 语义。Compiler/Ask 的生成入口和自由创建 Proposal 的编辑器属于后续范围。
