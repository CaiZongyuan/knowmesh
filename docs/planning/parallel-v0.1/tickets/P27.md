# P27: 真实进程退出恢复矩阵与 Doctor locator 检查

## Parent

[并行交付规格](../spec.md)；原任务 [#14](https://github.com/CaiZongyuan/knowmesh/issues/14)。

## What to build

用真实子进程退出验证已有 canonical transaction 的持久性，并让 Doctor 对 Evidence 的实际来源 bytes/quote/locator 给出诊断。用户在多文件写入被终止后可得到可解释、可重复执行的恢复路径。

## Acceptance criteria

- [ ] 真实进程 fixture 在 prepared 前后、每个目标替换后、canonical_committed 后和 DB commit 后退出，覆盖修改与新建、多文件 Proposal/Source/初始化场景；测试从磁盘重新打开进程与数据库，不仅构造内存状态。
- [ ] Doctor/sync 恢复取得正确锁，完整前滚或返回明确外部修改冲突；未完成事务不发布混合 projection，重复恢复不增加重复 generation、Proposal revision、receipt 或幂等绑定。
- [ ] 磁盘写失败、staging/manifest 缺失或损坏、before/after 之外的外部编辑、referenced Source bytes 改变均保留恢复材料并给出 typed diagnostics；已有 runtime 和备份可读性保持。
- [ ] Doctor 复用 parser/Evidence verifier 核对真实 immutable revision bytes、quote 和 locator，区别缺失来源、内容 hash 不符、解析质量不足与定位失败；只读检查不修复 offsets、不调用模型、不改历史证据。
- [ ] Doctor Core 输出 Schema/descriptor 与 CLI 保持一致；普通检查和 repair dry-run 无写入，确认 repair 仍只执行已有授权恢复动作，新增 locator finding 不被误解释为自动改写许可。
- [ ] 三平台可运行的 subprocess/integration fixtures 记录每个退出点的实际结果；配合架构 guard 验证诊断没有获得额外 canonical 写能力，现有 Apply/rebuild/initialization recovery 测试通过。

## Blocked by

None (ready after approved shared baseline).

## Scope and handoff

Canonical transaction/Doctor capability 拥有故障诊断与恢复验收，复用 `5247efe` 已有文件事务、Proposal receipt、Evidence verifier 和 parsers。共享热点是受控测试退出点、Doctor diagnostics Schema、journal/recovery 与 architecture policy；只修复本矩阵证实的问题，不重写已验证的 Apply/rebuild。停止于已有 canonical 工作流的真实进程矩阵和 locator diagnostics；P17 负责模型 Run 恢复，Server watcher/连接池排空与独立发布另有归属。
