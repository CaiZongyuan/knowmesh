# P14: 逐模型请求的持久预算、重试与控制接入

## Parent

[并行交付规格](../spec.md)；原任务 [#28](https://github.com/CaiZongyuan/knowmesh/issues/28)。

## What to build

每个实际发出的模型请求，包括 retry 和 structured-output repair，都在持久 Run 预算内先预留再结算，并可在调用期间观察停止信号。进程中断或换 attempt 后不能重置已花费的 token、费用和重试额度。

## Acceptance criteria

- [ ] 在每次 provider request 前原子保存输入/最大输出的预算预留与请求身份；预留失败或 tokens/cost/timeout 不足时 provider 未被调用，不能仅在整个 generate 返回后记录 aggregate。
- [ ] 成功按实际 usage 结算；无 usage、取消/超时或响应未落盘时保留保守预留并标记 estimated/usage_uncertain，迟到 usage 可计入原请求而不会授权发布结果。
- [ ] 单逻辑调用的 retry/repair、累计 tokens/cost 和剩余执行 timeout 持久化；沿用现有有界 backoff/jitter/Retry-After，鉴权/输入/Schema/policy 错误不盲重试，重新打开 store 不重置额度。
- [ ] max-cost 在价格未知时返回 configuration error；价格、provider/profile/sampling/context 限制属于固定语义，密钥轮换可以继续且不会泄漏 secret。
- [ ] 请求期间和重试等待期间可观察 attempt/control 变化并尝试中止网络；暂停等待不扣执行 timeout，已停止或旧 attempt 的成功不能被当成有效 stage 输出。
- [ ] 最高 Core 用例的可执行集成测试使用真实 SQLite 和可控 fake provider，覆盖预留前失败、发送后中断、unknown usage、retry/repair 累计、费用上限、停止信号和晚到响应；现有单次 generation 与 HTTP adapter 合同保持兼容。

## Scope and handoff

Run 拥有持久请求账本与预算，model generation 拥有结构化校验与单次逻辑调用；两者在实际 request 边界协作。共享热点为 ModelProvider/generation、Run port 和模型 adapter，须保持 P10–P12 的调用兼容。此票不新增临时 CLI/registry entry，以真实 Core/SQLite use case 验收；P15/P20 连接公开 compile/ask，P16 将用户控制操作传入此边界，P17 验证恢复。停止于逐请求可恢复控制，不声称远端仅执行/计费一次。
