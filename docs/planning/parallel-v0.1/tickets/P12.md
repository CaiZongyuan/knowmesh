# P12: Assertions 与 full 模式的完整 Proposal 规划

## Parent

[并行交付规格](../spec.md)；原任务 [#28](https://github.com/CaiZongyuan/knowmesh/issues/28)。

## What to build

Compiler 将已解析实体上的 Claim/Relation 候选、逐字证据、去重和冲突结果组合为 assertions/full Proposal。用户后续审核的是经过真实定位和 Schema 检查的计划，原始知识保持到 Apply 才改变。

## Acceptance criteria

- [ ] Assertions 模式只规划既有/已解析实体上的 Claim/Relation；full 模式同时包含 entities、assertions 和受控 summary，保留 P11 的唯一映射与 review 语义。
- [ ] 每条进入有效 Proposal 的 Compiler assertion 均通过固定 revision 的真实 quote/span/quality 验证并获得 Evidence 身份；无定位、跨边界或伪造引用被过滤并留下可判定 warning。
- [ ] 使用既有 exact dedup、语义 comparison 和 conflict planning；重复证据与主张合并规则保持 qualifiers/科学符号语义，冲突双方和 group review 状态可见。
- [ ] Builder 校验全部闭合 patch ops、目标、依赖、Schema、before hash、summary 管理边界与 policy；文件 before hash 始终来自原 canonical，不以 dedup 中间拟议状态替代，拒绝项不能留下不存在的目标引用。
- [ ] 所有模型 advice/comparison 使用共享 generation 预算接口，实际知识输入、规则与模型 identity 进入 stage 依赖；生成的 IDs/时间、usage、warnings 和完整计划随可验证产物保存，恢复不重新分配身份，规划从不直接写 canonical。
- [ ] 可执行 Core/SQLite 集成 fixtures 从 P10 候选到 Builder preview，覆盖有效主张、无证据、重复/矛盾、两个来源、partial-invalid 候选及 summary 保护；每个有效 assertion 的 locator validity 为 100%。

## Scope and handoff

Compiler 拥有已存在组件之间的 pipeline 编排和临时身份映射，复用 verifier、resolver、dedup/conflict、summary editor、Builder。共享热点是 stage 数据、模型调用入口和 ProposalInput；P14 可兼容接入逐请求控制，最终在 P15 汇合。此票以最高 Core 用例集成测试验收，不新增临时公开 operation；P15 才拥有 source.compile DTO/registry/CLI 与持久发布，P18 负责 refresh。停止于可验证的完整规划，不替代人工标注 Compiler release eval。
