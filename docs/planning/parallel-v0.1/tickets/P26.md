# P26: 显式 canonical migrate 预览、备份与版本拒绝

## Parent

[并行交付规格](../spec.md)；原任务 [#31](https://github.com/CaiZongyuan/knowmesh/issues/31)。

## What to build

用户通过显式 `migrate --to` 预览规范格式迁移；受支持的变更在执行前备份，随后走可恢复 canonical transaction。当前只定义 version 1 时，命令诚实返回无变更或不支持版本的 typed error。

## Acceptance criteria

- [ ] Core migrate 用例、Input/Output、Operation descriptor 和 CLI 明确 target version、dry-run、确认与幂等语义；当前 v1 到 v1 返回稳定 no-op，不改 canonical、generation 或创建无意义备份。
- [ ] 未定义 source/target version、未来版本或不受支持的版本对返回 typed error，保留原文件；不按旧结构猜测，不宣称存在未定义的已发布 v0 格式。
- [ ] 对明确支持的转换先生成完整文件 patch 预览，包含目标/变更和备份信息；dry-run 不写 canonical、runtime、备份或 staging，真实执行前重新验证输入版本与 before hashes。
- [ ] 执行要求确认，并在首个规范文件替换前完成所有受影响文件的可验证备份；备份失败阻止替换，后续失败保留材料并通过既有文件事务前滚或报告外部修改冲突。
- [ ] 同 key 重试不会重复变更或丢失首次结果，成功同步投影；只在有来源定义时加入真实版本转换规则，已支持转换的未知字段、非管理内容和引用按格式契约保留。
- [ ] CLI 覆盖 v1 no-op、unsupported source/target、dry-run 与确认；用明确标记的测试版本 fixture 验证实际 patch/备份/失败恢复协议，该 fixture 不构成公开历史格式支持声明。

## Blocked by

None (ready after approved shared baseline).

## Scope and handoff

Canonical migration 用例拥有支持版本清单和转换规划，复用既有 canonical scan、lossless writers、file transaction、backup/recovery 与幂等原则。共享热点为 canonical write capability、Operation registry/CLI、recovery journal 兼容性及 writer policy。停止于显式命令和经测试的预览/备份协议；SQLite schema migrations 是不同职责，格式版本转换必须有已定义输入依据，不能为完成票虚构历史支持。
