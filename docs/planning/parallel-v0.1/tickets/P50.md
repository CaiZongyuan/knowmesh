# P50 独立发布工作流与兼容性 fixture 矩阵

## Parent

[并行实施规格](../spec.md)；原始需求 [#45](https://github.com/CaiZongyuan/knowmesh/issues/45)。

## What to build

建立分别面向 cli-v* 与 web-v* 的发布工作流及兼容性 fixture 矩阵，先以 dry-run 和候选 artifact 验证构建、校验、包边界与发布顺序。生产发布需在 P54 完整验收后另获用户明确授权。

## Acceptance criteria

- [ ] 后端与 Web 工作流分别拥有版本、触发入口和产物清单；后端构建不构建或下载 Web，Web 构建不重新构建、打包或发布后端。
- [ ] dry-run 能完成候选原生包、安装器、npm 包或 Web 包的生成与清单校验，并保存实际结果；默认候选验证路径不创建生产 tag、release 或 npm 版本。
- [ ] 后端工作流先验证同版本原生 artifact 全部可获取且 checksum 正确，再允许引用它们的 npm 发布步骤；缺包、版本不一致或校验失败阻止后续发布。
- [ ] fixture 矩阵实际覆盖兼容 API 范围、低于最低版本、API major 不兼容、required capability 缺失与 optional vector 缺失；双方独立升级可运行，不兼容时显示可操作的错误且 CLI 保持可用。
- [ ] 兼容性测试使用固定对端 fixture 或 artifact 并记录来源与 hash；只把它作为测试依赖，不悄悄扩大组件的构建和安装依赖。
- [ ] 候选 release notes 自动或按模板汇总组件版本、API contract version/range、五平台状态、校验值、安装升级步骤、实测兼容组合和未验证项。
- [ ] 生产发布入口核对 P54 的通过证据以及针对具体版本与产物的用户发布授权；构建工作流的完成状态不依赖尚未执行的生产发布，也不自动批准发布。

## Scope and handoff

本票拥有发布工作流、artifact 清单连接和兼容性测试矩阵；复用 P47/P48/P49 的打包输出及现有 CI 检查。共享版本与 API 元数据变更必须协调。这里交付可审查、可 dry-run 的基础设施；P54 依赖该基础设施完成最终验收，之后的生产发布才反向读取 P54 结果，因此不形成实现依赖环。
